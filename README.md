# Ollama Cockpit拡張機能 要件定義書

-   文書種別：要件定義・基本設計
-   対象：Ubuntu上のCockpitに追加するOllama管理・チャット拡張機能
-   初版：1.0
-   言語：日本語

------------------------------------------------------------------------

## 1. プロジェクト概要

### 1.1 目的

Cockpitの管理画面からOllamaを操作できる専用拡張機能を開発する。

本拡張機能は、Ollamaの稼働状況・モデル管理・チャットを一元的に扱うことを目的とする。Cockpit標準のナビゲーションやデザインに統一し、既存のサーバー管理画面に自然に統合する。

### 1.2 基本方針

1.  Cockpit標準のUI・操作感に合わせる。
2.  バックエンド処理はPythonで実装する。
3.  Ollamaとの通信には原則として公式REST APIを使用する。
4.  Ollama APIをインターネットへ直接公開しない。
5.  初期版は既存のOllamaを同一Ubuntuホスト上で利用する。
6.  将来的に別ホストやGPU搭載サーバーのOllamaへ接続先を変更できる構造を目指す。
7.  既存のOpen
    WebUIとは独立した、Cockpit内の管理・操作用GUIとして開発する。

### 1.3 対象環境

  項目               想定
  ------------------ ------------------------------------------
  OS                 Ubuntu 24.04 LTS系
  管理UI             既存のCockpit
  LLMランタイム      既存のOllama
  Ollama API         初期設定 `http://127.0.0.1:11434`
  フロントエンド     HTML / JavaScript / CSS
  UIコンポーネント   Cockpit標準UIに適合するPatternFly
  バックエンド       Python 3
  設定保存           JSON等
  会話履歴           初期版はブラウザ側。将来SQLite対応を検討

## 3. 画面・機能要件

Cockpitのサイドメニューに「Ollama」を追加し、以下の画面を提供する。

### 3.1 ダッシュボード

#### 表示項目

-   Ollamaの接続状態
-   Ollamaのバージョン
-   インストール済みモデル数
-   実行中モデル数
-   実行中モデル名
-   CPU使用率
-   メモリ使用量・使用率
-   取得可能な場合はGPU情報
-   Ollamaのエラー・接続失敗状態

#### 要件

-   画面表示時に最新状態を取得する。
-   必要に応じて一定間隔で状態を更新する。
-   Ollamaに接続できない場合、画面全体を停止させず、接続エラーを明示する。
-   CPU・メモリ情報はCockpit既存機能やOS情報取得を活用する。
-   GPU情報は取得可能な環境のみ表示し、取得できない場合も正常動作とする。

### 3.2 モデル管理

#### モデル一覧

モデルごとに以下を表示する。

-   モデル名・タグ
-   ファイルサイズ
-   パラメータ数（取得可能な場合）
-   量子化方式（取得可能な場合）
-   モデルの詳細情報
-   実行中／停止中の状態

#### 操作

  操作           内容
  -------------- ----------------------------------
  一覧取得       インストール済みモデルを表示
  詳細表示       モデルの詳細情報を表示
  ダウンロード   指定モデルをOllamaから取得
  進捗表示       ダウンロードの状態・進捗を表示
  削除           選択したモデルを削除
  実行状態確認   現在ロードされているモデルを表示

#### 注意事項

-   モデル削除前に確認ダイアログを表示する。
-   ダウンロード中は進捗をリアルタイムまたは逐次更新する。
-   ダウンロード失敗時は理由を表示し、再試行できるようにする。
-   モデルの「ロード」「アンロード」はOllamaのAPI仕様に沿って実装する。専用の単純なロード／アンロードAPIが存在するものとして扱わず、生成リクエストやKeep
    Alive等を利用する場合は挙動を検証する。

### 3.3 チャット

#### 基本機能

-   モデル選択
-   メッセージ送信
-   ストリーミング形式の応答表示
-   生成停止
-   新規チャット
-   会話履歴の表示・切り替え
-   Markdown表示
-   コードブロック表示
-   コピー操作
-   Temperature等の生成パラメータ設定
-   Keep Alive等のリクエスト設定

#### 操作要件

-   応答を受信するたびに画面へ逐次反映する。
-   生成中であることを視覚的に表示する。
-   生成停止操作を提供する。
-   通信エラー・タイムアウト時にエラーを表示する。
-   選択モデルが利用できない場合は、ユーザーに分かる形で通知する。
-   会話履歴は初期版ではブラウザ側に保存する。
-   将来のSQLite移行を考慮し、会話データの構造をUI実装から分離する。

#### 初期版の会話データ項目案

-   会話ID
-   会話タイトル
-   使用モデル
-   メッセージ一覧
-   メッセージの役割（user / assistant）
-   メッセージ本文
-   作成日時・更新日時
-   生成パラメータ（必要に応じて）

### 3.4 設定

#### 設定項目

-   Ollama API接続先
-   デフォルトモデル
-   Keep Alive
-   Temperature
-   Context Length（num_ctx）
-   その他Ollamaがサポートする生成オプション

#### 要件

-   初期接続先は `http://127.0.0.1:11434` とする。
-   接続先の変更は管理者向け設定とする。
-   設定値の妥当性を検証する。
-   APIキー等の機密情報を扱う場合は、平文で不用意に保存しない。
-   OllamaのAPI仕様やバージョンによって利用できない項目がある場合は、適用可否を明示する。

## 4. システム構成

### 4.1 論理構成

``` text
Cockpit Web UI
  |
  | JavaScript / Cockpit API
  |
Cockpit Bridge
  |
  | cockpit.spawn() 等によるプロセス起動・入出力
  |
Python Backend
  |
  | HTTP REST API
  |
Ollama API (127.0.0.1:11434)
  |
Ollama Runtime
  |
Models / CPU / GPU / Memory
```

### 4.2 フロントエンド

使用技術：

-   HTML
-   JavaScript
-   CSS
-   Cockpit JavaScript API
-   PatternFly（Cockpitの採用バージョンに適合するもの）

役割：

-   画面表示
-   ユーザー操作の受付
-   Pythonバックエンドとの通信
-   ストリーミングデータの画面反映
-   入力値の基本検証
-   エラー・進捗表示

React等の大型フレームワークは初期版では必須としない。Cockpit標準の実装方式との整合性を優先する。

### 4.3 Pythonバックエンド

役割：

-   Ollama REST APIとの通信
-   APIレスポンスの整形
-   モデル情報取得
-   モデルのダウンロード・削除
-   チャットリクエスト処理
-   ストリーミング応答の中継
-   OS情報取得
-   設定の読み書き
-   エラー処理

初期版ではPython標準ライブラリを優先し、依存パッケージを最小限にする。必要に応じてHTTPクライアント等の外部ライブラリを採用する。

### 4.4 フロントエンドとバックエンドの通信

第一候補はCockpitのBridgeと`cockpit.spawn()`を利用し、Pythonプロセスとの標準入出力を介して通信する方式とする。

通信形式はJSON Linesを基本とする。

-   1行につき1つのJSONメッセージ
-   要求と応答を識別できるIDを付与
-   通常応答とストリーミングイベントを区別
-   標準出力にはプロトコルデータのみを出力
-   ログやデバッグ情報は標準エラー出力へ出力

ただし、`cockpit.spawn()`の実際の入力・出力・プロセス寿命・権限・ストリーム処理の仕様を実装前に確認する。CockpitのBridgeプロトコルと独自JSON
Linesを混同しないこと。

Pythonプロセスの起動方式、常駐の要否、複数リクエストの扱いはプロトタイプで検証して確定する。

## 5. Pythonバックエンド設計

### 5.1 推奨ディレクトリ構成

``` text
backend/
├── main.py          # エントリーポイント・要求ルーティング
├── ollama.py        # Ollama APIクライアント
├── system.py        # CPU・メモリ等の情報取得
├── config.py        # 設定の読み書き・検証
├── protocol.py      # JSON Linesの入出力
└── errors.py        # エラー定義・変換
```

### 5.2 Ollama APIの利用候補

  機能               API
  ------------------ ----------------------
  バージョン確認     `GET /api/version`
  モデル一覧         `GET /api/tags`
  実行中モデル一覧   `GET /api/ps`
  モデル詳細         `POST /api/show`
  モデル取得         `POST /api/pull`
  モデル削除         `DELETE /api/delete`
  チャット           `POST /api/chat`
  生成               `POST /api/generate`

APIのパス、HTTPメソッド、リクエスト形式、ストリーミング仕様は実装時点のOllama公式ドキュメントで確認する。

### 5.3 要求・応答プロトコル案

通常要求の例：

``` json
{
  "id": "request-001",
  "action": "models.list",
  "params": {}
}
```

通常応答の例：

``` json
{
  "id": "request-001",
  "type": "result",
  "ok": true,
  "data": {
    "models": []
  }
}
```

ストリーミングイベントの例：

``` json
{
  "id": "request-002",
  "type": "event",
  "event": "chat.delta",
  "data": {
    "text": "応答の一部"
  }
}
```

完了イベントの例：

``` json
{
  "id": "request-002",
  "type": "done",
  "ok": true
}
```

エラー応答の例：

``` json
{
  "id": "request-001",
  "type": "error",
  "ok": false,
  "error": {
    "code": "OLLAMA_UNAVAILABLE",
    "message": "Ollamaに接続できません"
  }
}
```

上記はアプリケーション内部の通信形式案であり、Cockpit
Bridge自体のプロトコルではない。

## 6. セキュリティ要件

1.  Ollamaの11434番ポートをインターネットへ直接公開しない。
2.  初期設定ではlocalhost経由でOllamaへ接続する。
3.  任意のシェルコマンドを受け付ける汎用実行機能を設けない。
4.  Pythonプロセスは必要最小限の権限で実行する。
5.  root権限を安易に付与しない。
6.  モデル削除など破壊的操作には確認を要求する。
7.  外部入力をコマンド文字列へ連結して実行しない。
8.  API接続先の変更は管理者に限定する。
9.  設定ファイルの権限を適切に設定する。
10. エラー出力やログにプロンプト・機密情報を不用意に記録しない。
11. チャット履歴の保存場所と削除方法を明確にする。
12. 複数ユーザー利用時は、履歴・設定・操作権限の分離を検討する。

## 7. 非機能要件

### 7.1 操作性

-   Cockpit標準のナビゲーション・配色・コンポーネントに合わせる。
-   画面遷移や基本操作を分かりやすくする。
-   長時間処理には進捗・実行中表示を設ける。
-   エラー時に原因と対処の手掛かりを表示する。

### 7.2 性能

-   モデル一覧など軽量な情報取得で画面を不必要にブロックしない。
-   チャット応答はストリーミング表示する。
-   大きなモデルのダウンロード中も画面操作を可能にする。
-   不要な高頻度ポーリングを避ける。

### 7.3 保守性

-   UI、Ollama API処理、OS情報取得、設定管理を分離する。
-   Ollama APIの変更に対応しやすい構成とする。
-   Python側の処理を単体テスト可能にする。
-   ログとエラーコードを整理する。

### 7.4 拡張性

-   将来的な複数Ollamaホストへの接続を考慮する。
-   GPU情報の取得処理を独立させる。
-   会話履歴の保存先をブラウザからSQLiteへ変更できるようにする。
-   生成パラメータを追加しやすい設計とする。

## 13. 開発方針のまとめ

本プロジェクトでは、Cockpit標準UIに統一したOllama専用の管理・チャット拡張機能を開発する。

フロントエンドはJavaScript、バックエンドはPythonとし、Cockpit
Bridgeを介して連携する。Ollamaとの通信は公式APIを利用し、モデル管理とチャットのストリーミング処理を実装する。

最初はCockpitへの登録、Pythonとの通信、モデル一覧表示までをMVPの基礎として完成させ、その後にモデル操作、チャット、監視・設定機能を段階的に追加する。
